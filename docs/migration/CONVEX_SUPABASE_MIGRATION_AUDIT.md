# Convex to Supabase Migration Audit

**Audit date:** 2026-11-03
**Scope:** repository source and local Supabase state. This continuation adds staged default-off people-discovery reads for the Messages people picker and count badge. Earlier Home Feed and profile-read entries describe separate workstreams. No production flags, backfills, deployments, or hosted/production Supabase were changed.

## Executive summary

Convex remains the active application backend. The repository AST audit (`scripts/audit-convex-api.ts`) reports **437 exported Convex functions** and **415 frontend references** to `api.module.function`, comprising **318 unique functions**. The frontend scan includes all `src/**/*.{ts,tsx}`, including tests. The inventory table at the start of this batch contained **58**, not 57, implemented-or-partial rows (38 IMPLEMENTED_NOT_FULLY_TESTED + 20 PARTIALLY_MIGRATED); the prior summary's 57/437 figure was an arithmetic/reporting discrepancy. Recounting the appendix after this batch gives **0 functions VERIFIED_COMPLETE**, **52 IMPLEMENTED_NOT_FULLY_TESTED**, **19 PARTIALLY_MIGRATED**, **289 LEGACY_DEPENDENCY**, **77 NOT_MIGRATED**, and **0 NOT_APPLICABLE**. The implementation indicator is **71/437 = 16.2%**, while strict verified coverage remains **0/437 = 0%**. Mocked Edge handler tests and local pgTAP do not establish imported-data reconciliation or staged-runtime behavior.

The function inventory is exhaustive for exported Convex query/mutation/action builders discovered by the current AST scan. Static matching is not evidence of behavior equivalence. All authorization, ownership, data parity, integration side effects, and frontend cutover must pass operation-level validation before a function can be considered complete.

## Method and status definitions

- `scripts/audit-convex-api.ts` uses TypeScript AST to count exported builders in `convex/` (excluding generated files) and frontend `api.module.function` expressions in `src/`. It found no unresolved frontend references. Reference totals include test-source references and do not represent live production call volume.
- Appendix status mapping is conservative. The replacement allowlist covers the currently identified narrow adapters. Other functions are categorized from static frontend/backend references. A statically referenced unmatched function is LEGACY_DEPENDENCY; no detected caller and no mapped replacement is NOT_MIGRATED (not proof it is dead). The appendix's table hints and caller strings are lexical scans and may miss indirect/dynamic calls. For authoritative headline frontend figures, use the AST audit totals above, not the appendix's simpler per-row caller hints.
- `VERIFIED_COMPLETE`: equivalent behavior, authorization, effects, frontend use, migration/data state and tests verified. None qualify.
- `IMPLEMENTED_NOT_FULLY_TESTED`: a corresponding Supabase path exists, but parity/cutover/runtime evidence is incomplete.
- `PARTIALLY_MIGRATED`: only part of the operation or feature is represented.
- `LEGACY_DEPENDENCY`: Convex operation has static callers and no verified equivalent replacement.
- `NOT_MIGRATED`: no replacement or static caller detected; investigate external/dynamic use before removal.
- `NOT_APPLICABLE`: not used here.

A previous Phase B report in temporary audit artifacts listed 413 functions; it is stale against the current AST result of 437 and is superseded.

## Frontend dependencies

`src/App.tsx` and `src/main.tsx` still construct/use Convex providers/client. `.env.example` retains `VITE_CURRENT_USER_BACKEND="convex"`. `src/lib/supabase.ts` configures a Supabase client and existing provider token flow, and selected adapters use Supabase for current user/profile mutations, notification preferences, waitlist, recent searches, feed reads and wallet paths. Notification reads/subscription mutations have a separate `VITE_NOTIFICATIONS_BACKEND` selector whose default is Convex; it was not set here. The selector does not cover all frontend features. Direct Convex hooks/API calls remain across contexts, components and admin areas. No production/backend flag value was changed.

## HTTP, scheduled work, storage, realtime and integrations

- `convex/http.ts`: `POST /api/webhooks/vtu`, `POST /api/webhooks/bachs`, `GET /api/payments/bachs/callback`. Bachs Edge Function exists, but forwards some classes to Convex; no equivalent VTU or callback route was identified.
- `convex/crons.ts`: daily `internal.subscriptions.processDueRenewals` and `internal.creators.maintainCreatorSubscriptions`. No local Supabase scheduler is configured. Convex also uses `ctx.scheduler.runAfter`; enumerate delays, retries, idempotency and side effects before replacement.
- Convex storage upload URL, URL lookup and delete paths remain in users, sounds, social, cycles and other features. No Supabase Storage bucket, policies or frontend storage adapter exist. Cloudinary/Mux are feature-specific integrations, not a general storage migration.
- Convex reactive query subscriptions remain. No published Supabase tables or equivalent realtime adapter was found.
- ClubKonnect, Resend, OneSignal, Agora, Mux, Cloudinary, Cloudflare, Bachs, VTU, payment, subscription, advertisements, moderation and admin integrations need per-operation test evidence. Configured credentials do not prove a migrated integration.

## Security and authorization work

Service-role-only SQL access with zero direct-client policies means Edge handlers must authenticate first and enforce ownership/admin scope before any privileged query or RPC. Shared Firebase/Playsole JWT verification and explicit-plus-legacy identity consistency exist, but this inventory does not prove every Convex operation's authorization semantics are reproduced. Required review includes wallet balances/transactions/PIN/OTP, identity provisioning/linking, private search, social privacy, chat membership, admin operations, audit logs, payment replay/idempotency and media access. Preserve Bachs' separate webhook signature verification. No hosted gateway test is claimed.

## Tests and unverified behavior

The package test scripts include auth identity policy, wallet flows, payment history, feature tests, Bachs, social connections, JWT verification, shared auth middleware, app-user authorization, feed auth, schema generation, Supabase transport/current-user/webhook/search security. Dedicated wallet PIN and Edge Function harness tests exist. These do not establish full feature parity, live provider delivery, hosted JWT gateway behavior, complete data reconciliation, storage/realtime/scheduler operation, or complete Supabase-only frontend behavior. **No automated tests were executed during this audit turn.**

## Top five blockers

1. **Frontend cutover:** 415 static Convex references across 318 unique operations; Convex provider/client remains active and the backend default is Convex.
2. **Feature parity:** broad admin, social write, groups/chat, calls, pages/shops/events, rewards, subscriptions/ads and moderation coverage remains absent or incomplete.
3. **Data/reconciliation:** snapshot validation/import tools exist, but no historical records were backfilled or reconciled; wallet/payment balances and references need a controlled plan.
4. **Authorization completeness:** privileged service-role access and zero direct RLS policies require a verified per-operation auth/ownership/admin matrix and negative tests.
5. **Runtime lifecycle/integrations:** cron and one-off jobs, VTU/Bachs callbacks, media storage and realtime have no fully verified Supabase replacements.

## Prioritized implementation roadmap

### Batch 1 (recommended): finish identity and profile lifecycle
- **Operations/tables:** `users.*`, `authIdentities`, `authLinkChallenges`, user profile/onboarding fields.
- **Frontend:** AuthContext/current-user provider, profile and onboarding screens; retain Firebase/Playsole sessions and existing Lalao IDs.
- **Server:** complete `app-user` provisioning and profile semantics without Supabase Auth replacement.
- **Security:** signature/issuer/audience/subject validation, explicit+legacy mapping consistency, no email-only linking, derive user ID from verified identity, preserve role.
- **Tests:** valid/invalid/expired Firebase and Playsole JWTs; missing/unlinked/conflicting identity; provisioning/linking; profile ownership; admin-role preservation and frontend fallback.
- **Dependencies/risks:** account-link policy and historical mappings.
- **Completion:** per-operation parity matrix, local SQL/Edge integration tests, current frontend adapter coverage, and no mismatched identity across providers.

### Batch 2: social graph/content writes
Map posts, comments, reactions, follows, blocks, close-friends, reports, cycles and sounds; implement owner/privacy checks; test cross-user/private visibility, idempotency, pagination and side effects. Depends on identity and media strategy.

### Batch 3: chat/groups/calls/notifications
Map conversations, group membership, messages, calls, notifications and push tokens; enforce membership on every read/write; preserve OneSignal/FCM and Agora; validate realtime, reconnect and delivery.

### Batch 4: commerce/payments/wallet parity
Map wallet, market, creator monetization, orders, subscriptions, Bachs and VTU event classes; verify provider signatures, idempotency, reconciliation and failure recovery in provider sandbox with concurrency tests.

### Batch 5: jobs, storage and remaining platform
Map ads/rewards/admin/moderation/pages/shops/events, media lifecycle and cron/scheduler workflows; add observability/retries, audit controls, signed upload/access policy and data reconciliation tests.

For each batch, do not mark completion until every included operation has equivalent input/output/side effects, server-derived identity, ownership/admin checks, caller migration, tests, and rollback/data plan.
