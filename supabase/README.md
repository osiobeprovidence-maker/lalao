# Local Supabase foundation

This is an initial, local-only PostgreSQL schema generated from the current `convex/schema.ts`. It contains no user data and is not linked to a hosted Supabase project.

## Rebuild and verify the migration source

```powershell
npm run supabase:schema:test
npm run supabase:schema:generate
```

The generator refuses to overwrite an existing migration unless explicitly given `--force`. Review generated diffs before regenerating. `supabase/schema-coverage.json` records table, field, index, and relationship coverage.

## Start a local database

The project-scoped Supabase CLI is installed as a dev dependency (`supabase` `^2.122.0`; verified CLI 2.122.0). Docker CLI/daemon and `psql` were unavailable in the checked environment. `wsl --status` returned Access denied, so WSL readiness is unknown. `supabase/.temp/project-ref` is absent and the checked-in config uses `project_id = "lalao-local"`; no hosted project is linked. Do not run `supabase link`, `supabase db push`, or `--linked` commands during this local phase.

Supabase's Windows local stack needs a Docker-compatible runtime. Docker Desktop can be installed from [Docker's official installation page](https://docs.docker.com/desktop/setup/install/windows-install/). Docker supports a per-user install that normally does not need administrator access. From the directory containing the downloaded installer, run:

```powershell
Start-Process -FilePath ".\Docker Desktop Installer.exe" -ArgumentList "install", "--user", "--backend=wsl-2", "--no-windows-containers" -Wait
```

If WSL 2 is missing or needs enabling, Windows may require an administrator PowerShell and a restart; Docker Desktop's WSL backend requires WSL 2. Confirm with `wsl --version` and `wsl --status` after setup. Start Docker Desktop from the Start menu and verify the daemon using `docker version`.

After Docker is running and `docker version` succeeds, from the repository root start the local stack, apply the local migration to the local database, and run the SQL contract suite:

```powershell
npx supabase start
npx supabase db reset
npx supabase test db
```

`db reset` deletes this project's local database contents. Before running it, confirm whether any local database data must be preserved; do not reset if it does. It applies checked-in migrations and config disables seed loading. The pgTAP suite uses synthetic users and search rows in a rollback-only transaction. The mocked REST adapter tests also use synthetic request values.

### Repeatable local validation checklist

From the repository root, after Docker Desktop is running:

```powershell
npm run supabase:schema:test
npx supabase start
npx supabase db reset
npx supabase test db
npm test
npm run build
```

`supabase test db` includes deterministic pgTAP cases for recent-search sync, profile updates/avatar cleanup, notification preference validation, Web Push subscription maintenance, notification read authorization, and waitlist eligibility. These tests use synthetic rows and roll back their transactions. The profile preference/waitlist cases can be run directly with `npx supabase test db --local supabase/tests/database/profile_preferences_waitlist.test.sql`; notification cases use `npx supabase test db --local supabase/tests/database/notification_runtime.test.sql`. Then locally enable `SUPABASE_RECENT_SEARCHES_SHADOW=true` only in a local Convex dev deployment, set its URL to the local Supabase API and its local service-role key, and exercise search/update/remove/clear with synthetic accounts. Check the scheduler's retries and confirm Convex's recent-search query remains the only read path. Never copy these values to production.

## Schema and access behavior

- Convex document IDs remain text in `_id`; `_creationTime` and application timestamps retain epoch-millisecond numeric values.
- Current scalar validators, optionality, literal unions, JSON-shaped values, indexes, and scalar `v.id` relationships are represented in SQL. Convex search indexes are represented as PostgreSQL full-text GIN indexes.
- Convex indexes are non-unique by default. Unique indexes are added only for the source-documented identity keys and Bachs webhook event ID.
- Scalar relationships use `ON DELETE NO ACTION`, deferred constraints, and `NOT VALID`; cascade behavior has not been inferred. Seven top-level `_storage` references (`users.avatarStorageId`, `posts.mediaStorageId`, `comments.mediaStorageId`, `messages.mediaStorageId`/`audioStorageId`, `cycleStories.mediaStorageId`, and `sounds.audioStorageId`) and one nested JSONB reference (`adCampaigns.creative.mediaStorageId`) need an object-store mapping. Three user-ID arrays (`groupChats.memberIds`, `groupCycles.memberIds`, `cycleStories.excludedUserIds`) remain JSONB to preserve source semantics pending lifecycle review. `posts.soundId` is polymorphic (`sounds` ID or free-form string) and remains text without an FK.
- Every application table has RLS enabled, no `anon`/`authenticated` grants, and no user policies. `service_role` access is for trusted server code only and bypasses RLS; every server adapter must authenticate the Convex caller and enforce resource ownership itself.
- Existing `walletPin` and `pinResetOtp` fields are retained for schema parity. Do not import values from these plaintext fields; credential hashing and a compatibility plan are still required before any data migration.

The snapshot preflight blocks any wallet document containing `walletPin` or `pinResetOtp` and reports only the number of affected documents, never their IDs or values. The current wallet implementation compares PINs as plaintext, so do not hash values offline and import them: first migrate PIN set/change/transfer/reset verification to a server-side password-hash implementation, then clear legacy PIN and OTP values from the export. Until that wallet-flow change is deployed and verified, affected users must set a new PIN after cutover.

## Preserving Firebase and Playsole sign-in

Firebase ID tokens and Playsole ID tokens remain the identity credentials. The four user-facing Edge Functions (`app-user`, `app-search`, `app-social`, and `app-wallet`) verify those tokens in `_shared/verifyLalaoJwt.ts` against provider-specific, fixed JWKS URLs and issuer/audience allowlists. Their local gateway `verify_jwt` setting is disabled so the provider JWT reaches this mandatory in-function verifier; do not remove `withLalaoAuth` or expose these handlers without it. The middleware creates a service-role client only after cryptographic verification, resolves the verified issuer/subject through existing identity mappings, and supplies the mapped Lalao user ID to the handler. Provider `role` claims do not grant Lalao authorization. `app-bachs-webhook` remains independent and retains its Bachs signature verification. This implementation does not change Firebase, Playsole, Resend, frontend selection, hosted settings, or deployment state.

`VITE_CURRENT_USER_BACKEND=supabase` routes direct current-user profile reads in `App`, `LalaoContext`, Wallet, onboarding guards/setup, and Settings through the `app-user` Edge Function. Authenticated `users.getUserByUsername` callers (`UserProfileModal` and `MangaPublisherProfilePage`) also use the function under the flag; when the flag is off or the visitor is unauthenticated, the existing Convex query remains active. The Edge Function requires an authenticated provider token mapped to a Lalao user, matches usernames exactly, returns an explicit public-field projection, hides suspended accounts and suspended/closed creator details, and exposes date of birth only when visibility is `public` (age-only profiles receive only a calculated age). Email, phone, auth identifiers, roles, wallet/security values, precise coordinates, creator earnings, and other administrative fields are excluded. The users schema does not persist public/private profile visibility or blocked-user relationships; those access rules cannot be enforced by this operation until a source model and equivalent policy exist. Current-user profile reads, Firebase email/Google signup and login provisioning, onboarding profile writes, Settings profile and notification-preference writes, feed-interest edits, and country-restricted waitlist entry also use the function under the flag. Supabase-mode avatar uploads use authenticated Cloudinary signatures scoped to `avatars/<user-id>`; the profile stores the resulting public ID and queues prior tracked Cloudinary assets for retryable cleanup on later profile writes. Cleanup failures are reported as pending for retry; no scheduled cleanup worker is configured. Configure `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` as Edge Function secrets; never expose the API secret to the browser. The avatar MIME and 5 MB checks currently exist only in the UI and are not enforced by the signing endpoint. Cloudinary calls were tested with mocks only. Existing Convex Storage references and older Cloudinary URLs without trusted public IDs are preserved and are not automatically deleted. This remains a staged vertical slice, not a platform-wide switch: other Convex reads/mutations, topic recommendations, and Playsole's account-resolution/linking flow remain on Convex. The flag defaults to Convex. Keep it there until provider claims, migrated identity/profile rows and storage mappings are configured, then verify the complete signup, login, profile, and onboarding flows against a local Supabase stack.

Wallet balance/history reads and Batch wallet funding initialization/verification now also route through `app-wallet` when `VITE_CURRENT_USER_BACKEND=supabase`. The Edge Function resolves identity from the provider JWT, keeps the Batch secret server-side, reserves a user-owned payment reference, verifies the checkout session directly with the existing Batch API, then calls a service-role-only SQL settlement RPC that locks the funding reference and credits the wallet and ledger atomically and idempotently. Wallet transfers, PIN set/change/reset, crypto transfers, rewards, and utility purchases still use Convex. In particular, the PIN paths must be rebuilt with server-side password hashing and OTP protection before wallet operations can fully leave Convex. The `app-bachs-webhook` Edge Function verifies Batch V2/legacy HMAC signatures and replay timestamps. After its hosted deployment, point Batch at `/functions/v1/app-bachs-webhook`; wallet funding settles in Supabase, while other Batch references are forwarded with their original signed body to the configured HTTPS `CONVEX_SITE_URL` until those purchase flows migrate. `CONVEX_SITE_URL` must be a trusted `*.convex.site` URL. The hosted webhook URL has not been changed here. Batch session responses and sandbox payments have not been exercised here.\n\nThe initial SQL intentionally grants no `anon`/`authenticated` table access and defines no user RLS policies. Before direct client data access is enabled, design and test resource-specific policies using issuer plus subject (the provider subject is text, not Supabase `auth.uid()` UUID), and do not grant client access to wallet PIN/OTP fields or privileged payment/subscription state. Supabase custom OIDC integrations cannot be declared in the local CLI config; they require hosted Dashboard or Management API setup. Provider onboarding, claims, and policies are therefore a hosted auth gate, not something this local schema test can prove.

`VITE_PROFILE_READS_BACKEND=supabase` routes `social.getRelationship`, `social.getMyFollowers`, and `social.getMyFollowing` through authenticated `app-social` reads from `UserProfileModal` and `ProfileView`. The handlers use the current-user ID resolved by `withLalaoAuth`, query the existing `follows`/`pageFollowers` tables, omit suspended accounts, and return explicit user/page projections; page contact details and private user account fields are not selected. Historical Convex Storage avatar IDs are not resolved on these reads. When the flag is disabled, or a profile visitor is unauthenticated, the existing Convex query remains active. These handler tests use mocked Supabase results; no real database or staged-runtime integration was run.
This routing is now governed by `VITE_PROFILE_READS_BACKEND=supabase`, independent of the current-user and Home Feed flags. `social.listUserPosts` has a separate authenticated Edge page read using an explicit post projection, server-resolved viewer ownership, public-only visibility for other viewers, removed/suspended-profile filtering, and a stable `(createdAt, _id)` cursor. Its profile UI callers intentionally remain on Convex because the current profile feed response also supplies reactive likes/comments state; those features are outside this migration batch. The `idx_posts_profile_author_order` index supports the bounded page query. Tests use mocked Supabase data; local pgTAP verifies the index and browser-role access only. User-level private-profile settings and block relationships do not exist in the source model, so those semantics remain unresolved.

User follow/unfollow writes are staged through `app-social` by all current `toggleFollowUser` UI callers (global context callers, onboarding recommendations, and `AddPeopleModal`). Forward-only migrations `20261109000000_social_follow_lifecycle.sql` and `20261110000000_social_follow_lock_order.sql` add a service-role-only RPC, a unique `(followerId, followingId)` index, and deterministic sorted user-row locking. The RPC resolves no identity itself: the Edge Function supplies only the user ID already mapped from the verified provider token. A transaction-scoped advisory lock serializes each directed pair; the operation rejects self-follows/missing users, toggles the edge, updates both counters without going below zero, and creates the in-app `follow` notification atomically. Duplicate requests intentionally preserve Convex toggle semantics (a subsequent toggle unfollows); the database uniqueness constraint prevents duplicate rows. Local pgTAP covers sequential follow/unfollow, counters, notification shape, access grants, and invalid requests. Separate local PostgreSQL tests exercised concurrent same-pair and reciprocal toggles; the API tests use mocked RPC responses.

Notification listing/read state and Web Push subscription maintenance now have authenticated `app-social` operations. Forward-only migration `20261111000000_notification_read_and_push_subscriptions.sql` adds a unique endpoint index and service-role-only RPCs; it safely aborts if local/target subscription rows contain duplicate endpoints. The handlers derive ownership from `withLalaoAuth`, return notification actors using an explicit public projection, preserve the source notification limits, and restrict subscription deactivation to the mapped owner. `social.listNotifications`, push status, and subscription registration/deactivation are routed through a separate opt-in `VITE_NOTIFICATIONS_BACKEND=supabase` flag; it is unset/default-off. Keep it off until all notification producers and push dispatch are migrated together, because likes/comments and most other producers still write only to Convex. `social.getUnreadNotificationCount` has an Edge operation but no current caller and remains NOT_MIGRATED in the function inventory. Convex defines no notification delete/clear operation.

The Home Feed read path has a separate default-off `VITE_HOME_FEED_BACKEND=convex` switch. Authenticated For You and Nearby reads can use `app-social`; Following and topic/community tabs remain on Convex. The Edge handler resolves identity from the verified provider token, rejects client-supplied identity, uses explicit post/author/page projections, limits recent candidates, filters removed posts, and withholds non-public posts by other authors because group/page membership authorization is not represented in this path. `20261114000000_home_feed_order_index.sql` adds a recent-feed ordering index; source indexes already cover creation-time filtering and topic preferences. The index migration and six pgTAP checks were applied/run against local PostgreSQL only. Standard `supabase migration up --local` is currently blocked by a separately present same-version `20261113000000_social_post_comment_interactions.sql` file containing a SQL syntax error; that file was not edited or applied, and the feed index migration alone was applied and recorded locally. The local API tests use mocked Supabase results, and `home_feed_read.test.sql` checks index/RLS grants against local PostgreSQL. No block relationship model or block filtering exists in the source schema/feed query; do not enable the flag until compatible block and restricted-audience semantics are defined. The current Home Feed UI has no pagination/load-more flow, and its numeric timestamp cursor does not return a stable next cursor, so complete pagination parity remains a blocker. Convex remains the fallback and default; no feed UI redesign or current-user flag change was made.

Post and comment/reply like toggles have a separate, default-off `VITE_SOCIAL_INTERACTIONS_BACKEND=supabase` gate. Migration `20261112000000_social_like_notifications_outbox.sql` adds a unique `(userId, targetType, targetId)` like index and authenticated-server-only transactional toggle RPCs; `20261113000000_social_outbox_writer_permissions.sql` makes the shared outbox writer internal to those RPCs. The RPCs serialize on the target row, update counters, preserve the source notification types/deep links, suppress self-notifications, and create in-app notifications together with preference-aware outbox rows. The first migration aborts without deleting data if preexisting duplicate like keys are found. Run `npx supabase test db --local supabase/tests/database/social_likes_outbox.test.sql` for local PostgreSQL coverage. The outbox records pending/suppressed push work, but no worker, retry executor, or OneSignal/Web Push/FCM adapter consumes pending rows; this is not push delivery parity. Keep both notification-related flags off. Comment creation/replies remain on Convex because group/reply authorization and Convex Storage media URL resolution are not yet represented in the Supabase path.

The public-profile read accepts only an exact username, requires verified provider identity mapped to a Lalao profile, and returns a safe field allowlist. It omits private DOB values and privileged fields and suppresses suspended accounts and suspended/closed creator metadata. Unauthenticated visitors and flag-off callers use the sanitized Convex fallback. No user-level private-profile or block-relationship fields exist in the persisted source schema, so blocked/private-profile access rules remain an explicit blocker rather than inferred behavior. Tests for the Edge handler and projection use mocked database responses; no hosted or end-to-end integration was run. The function checks provider issuer, audience, and `role=authenticated`, and scopes identity lookup to the verified issuer/subject. Profile creation uses a transactionally idempotent service-role-only RPC with per-identity/email locks; browser-supplied profile hints cannot override signed JWT claims. Onboarding, preference, waitlist and profile operations use service-role-only RPCs with explicit operation and field whitelists; profile updates serialize exact-case username checks and keep legacy storage IDs out of client writes. New avatar uploads are signed into a user-specific Cloudinary folder; tracked old Cloudinary assets are placed in a service-only cleanup queue and retried on later profile writes. Legacy Convex Storage objects and preexisting Cloudinary assets without trusted IDs are preserved. Configure the three Cloudinary secrets listed above before enabling Supabase-mode avatar uploads. The UI's MIME/5 MB avatar restrictions are not server-enforced, and tests used mocked Cloudinary responses only. Playsole account resolution/linking and other profile mutations remain Convex. These paths are locally tested only; the user snapshot/data state and hosted runtime remain unverified. Separately, recent search reads, record, remove, and clear operations can route through the `app-search` Edge Function under the same flag. It resolves the signed-in provider identity to the canonical Lalao profile, scopes every query to that profile, enriches saved people/pages from Supabase, and applies writes through service-role-only SQL functions that maintain shadow revision state and deletion tombstones. ## Local snapshot validation (read-only)

The snapshot validator reads an already available local Convex export directory in the layout `<table>/documents.jsonl` (as used by the repository's existing restore scripts). It does not invoke the Convex CLI, contact Convex/Supabase, write into a database, or change files in the snapshot. It validates all source tables and their declared fields, checks duplicate document IDs and dangling scalar table IDs, and reports counts plus structural issue messages without printing record contents or IDs. It counts unresolved storage IDs (including nested creative metadata), ID arrays, and polymorphic references; it does not infer their target mapping. It is a preflight checker, not an importer or a substitute for database constraints/reconciliation.

```powershell
npm run supabase:snapshot:validate -- --snapshot-dir "C:\path\to\local\snapshot_extracted"
```

The command is dry-run only and exits nonzero if any source table file is missing or any structural issue is found. Treat local export contents as sensitive; use only an authorized, encrypted local copy. No export was performed for this validation. Existing `scripts/restore_relational_data.cjs` and `scripts/restore_snapshot_data.cjs` are not safe migration tooling: they contain hard-coded remote Convex destinations and may write data. Do not run them; a future importer must be redesigned with explicit local endpoint allowlisting, dry-run/reconciliation, backup and rollback controls.

Synthetic unit coverage is run as part of `npm run supabase:schema:test`. It validates a schema-complete 102-table fixture, a duplicate ID, a dangling scalar reference, and that the report omits IDs/values. PostgreSQL-backed constraints and pgTAP still require Docker plus the Supabase CLI.
